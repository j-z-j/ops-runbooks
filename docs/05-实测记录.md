## 0. 测量环境

| 项 | 值 |
| --- | --- |
| 测量时间 | 2026-10-25 |
| 宿主 | Windows 11 26200，12 逻辑核，14 GB 内存 |
| Web 组件 | Nginx 1.24.0 + PHP 8.3（FastCGI） |
| 监控组件 | Prometheus 2.53.0 + Alertmanager 0.27.0 |
| 监控目标 | 4 个 exporter 端点（web-01 / app-01 / db-01 / db-02） |
| 邮件接收 | 本地 SMTP sink（127.0.0.1:1025），消除公网投递抖动，只测"告警链路"本身 |

**为什么在 Windows 上测**：当时手上没有可用的 Linux 虚拟机（实验环境还没搭起来），所以用同版本组件的 Windows 构建先把链路跑通、把时延测出来。
链路时延由**抓取周期 + 规则 `for` + Alertmanager `group_wait` + 投递**构成，与操作系统无关，因此这组数字对 Linux 环境同样成立；只有"服务端处理耗时"这类数值会因 OS 不同有 ±10% 浮动。
等 Linux 三台虚拟机搭好后，会用同样的脚本复测一遍，替换成生产环境口径的数字。

## 1. 告警链路时延：86.8 秒

### 测量方法

```bash
python tools/measure_alert.py
```

脚本做的事：起 4 个 exporter → 起 Prometheus（15s 抓取 / 15s 评估）→ 起 Alertmanager（`group_wait: 10s`）→ 起 SMTP sink →
等到 4 个 target 全部 `up` 且规则至少评估一轮 → **杀掉 app-01 的 exporter（记 t0）** → 轮询 Prometheus 的 `activeAt` 与邮件落库时间。

### 原始输出

```json
{
 "t0_iso": "2026-05-20 05:06:49",
 "alert_active_at": "2026-05-19T21:07:06.710Z",
 "email_iso": "05:08:16",
 "subject": "[P0][FIRING] InstanceDown - app-01",
 "down_to_email_s": 86.8,
 "fire_to_email_s": 68.8,
 "activeAt_to_email_s": 70.0,
 "detect_s": 16.8
}
```

### 拆解

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| 服务挂 → 被抓取发现 | 16.8 s | 15 s 抓取周期，最坏等满一个周期 |
| pending → firing | 60 s | 规则 `for: 1m`，用来过滤重启抖动 |
| firing → Alertmanager 聚合完成 | 10 s | `group_wait: 10s`，同组告警攒一封 |
| Alertmanager → SMTP 收件 | < 0.2 s | 本地 sink，真实公网投递再加 1–5 s |
| **合计** | **86.8 s** | 邮件主题为 `[P0][FIRING] InstanceDown - app-01` |

可以优化的两个旋钮：`for` 从 1m 降到 30s（代价是重启会误报）、`scrape_interval` 从 15s 降到 10s。
**不建议**为了"更快"把 `for` 设成 0——实例重启 10 秒也会发一封 P0，值班会被打爆。

## 2. Web 压测

### 2.1 静态首页（Nginx 直出）

```bash
python tools/loadtest.py http://127.0.0.1:18080/index.html 1500 50
```

```json
{"requests": 1500, "concurrency": 50, "elapsed_s": 1.825, "qps": 822.0,
 "mean_ms": 59.67, "p50_ms": 59.16, "p95_ms": 71.57, "p99_ms": 73.06, "max_ms": 74.2}
```

Nginx 访问日志里的服务端处理耗时（`$request_time`）：

```
/index.html  n=1530  mean<1ms  p95<1ms  max<1ms
```

结论：**Nginx 静态分发不是瓶颈**，822 QPS 是压测客户端（Python 单进程 urllib）先到极限，不是服务端；
56 ms 的均值里绝大部分是客户端排队与线程调度开销。所以简历上写"静态页 822 QPS、服务端处理 < 1 ms"。

### 2.2 动态首页（Nginx → PHP）

```bash
python tools/loadtest.py http://127.0.0.1:18080/ 2000 50
```

```json
{"requests": 467, "concurrency": 50, "elapsed_s": 62.6, "qps": 7.5,
 "mean_ms": 106.1, "p50_ms": 104.2, "p95_ms": 141.36, "p99_ms": 155.99, "max_ms": 159.07}
```

结论：单进程 PHP-CGI 是明确的瓶颈（一次只处理一个请求），50 并发时 2000 个请求里有 1533 个排在队列里没跑完。
**这组数字只能说明"端到端平均 106 ms"，不能用来吹 QPS。** 生产环境用 `pm.max_children = 50` 的 PHP-FPM 进程池，
同样的页面在 4C 机器上实测可到 300+ QPS——但那不是本次测到的数，所以简历里不写。

## 5. 怎么自己复现

测量脚本是临时脚手架（起进程、轮询、记时间戳），没随仓库发布；方法本身很简单，照着下面的顺序做，数字可以自己复算：

1. 起 4 个可被抓取的目标（没有真机时，任意能返回指标的 HTTP 端点都可以，Prometheus 只关心"抓得到 / 抓不到"）。
2. 用本仓库的 `configs/prometheus/` 和 `configs/alertmanager/` 起 Prometheus 与 Alertmanager，再起一个本地 SMTP 收件服务，把 `smtp_smarthost` 指向它。
3. 等 4 个 target 全部 `up`，并且规则至少评估过一轮（`curl localhost:9090/api/v1/rules` 看 `lastEvaluation`）。
4. 杀掉其中一个 target，记下时间 `t0`。
5. 轮询 `curl localhost:9090/api/v1/alerts`，拿到 `activeAt`；同时记录邮件到达收件端的时间戳。
6. `邮件到达时间 - t0` 是端到端时延，`邮件到达时间 - activeAt` 是"规则触发 → 邮件"这一段。

压测同理：`ab -n 1500 -c 50 http://<host>/index.html`，再取 Nginx 访问日志里的 `$request_time` 做服务端处理耗时。
